# Как пополнять репозиторий. Для ИИ из любого чата

Человек правит этот репозиторий из разных чатов и сессий Claude. Без общих правил правки мешают друг другу: одно правило записано дважды с разными цифрами, старый совет лежит рядом с новым, индексы отстают, два чата выбирают один и тот же номер раздела. Читай этот файл до первой правки. Всё ниже обязательно. Цель в том, чтобы каждая правка делала структуру лучше, а не длиннее.

## 1. Перед правкой

1. Подтяни свежий main: `git pull --rebase origin main`. Версия из начала чата могла устареть, пока человек правил из другого чата. В чате без git склонируй репозиторий заново.
2. Прочитай `CLAUDE.md`, карту в `README.md` и целиком тот файл, куда собираешься писать.
3. Найди, где тема уже описана: `grep -rn "слово" .` по двум-трём словам правила и по числам из него. Нашёл, правь существующее место, а не добавляй рядом.
4. Реши по таблице ниже, что куда идёт. Одна реплика человека часто даёт сразу правило, урок и факт. Раскладывай по местам, а не вали всё в один файл.

## 2. Куда что класть

| Что это | Куда |
|---|---|
| Правило для любого ролика, одна-две строки | `CLAUDE.md`, подходящий раздел |
| Как выполнять этап: шаги, пороги, формат отчёта | навык этапа в `.claude/skills/` |
| Почему так: что сломалось, что сказал человек, цифры, доказательства | `reference/lessons.md`, в конец |
| Устройство сервиса или движка: TTS, площадки, стек, конвейер | `reference/tts.md`, `platforms.md`, `tech_matrix.md`, `pipeline.md` |
| Не проверено, не уверен | `reference/unverified.md` |
| Внешняя страница, на которую опираемся | `reference/sources.md` |
| Готовый текст для Claude Code | `prompts/`, модель указана в заголовке |
| Скрипт проверки | `tools/` и строка в `tools/README.md` |
| Файлы проекта: видео, звук, ключи, `.env` | не в репозиторий, см. `.gitignore` |

У каждой темы в навыках один владелец, чтобы не дублировать:

| Тема | Навык |
|---|---|
| культурный код, аутентичность, шрифты и ассеты | `video-style-dna` |
| вопросы до старта, бриф | `video-brief` |
| манифест стиля, стоп-кадры | `video-art-direction` |
| голос, ударения, тайминг, сведение звука | `video-voice` |
| проверки, ревью, формат отчёта | `video-qa` |
| Reels для бизнеса, выбор трека для рекламы | `video-reel-craft` |

Не уверен, куда класть: допиши в конец `lessons.md` с пометкой «к разбору» и скажи человеку. Новые файлы и папки без причины не создавай. Новый навык заводи только для новой стадии или нового жанра, с `description` в стиле соседей («Use when …»).

## 3. Один факт, три слоя

Правило может жить в трёх слоях: строка в `CLAUDE.md`, процедура в навыке, история в `lessons.md`. Это нормально, если все три говорят одно и то же. Остальные места дают только ссылку «см. …». Меняя число или формулировку, найди все слои через `grep` и поправь их в одном коммите. Абзацы не копируй.

## 4. Новое противоречит старому

- Не клади новое рядом со старым. Найди все места со старой версией (`grep`) и исправь их в этом же коммите.
- Историю не стирай. В `lessons.md` старый текст оставь и допиши пометку «Заменено: см. «заголовок», дата».
- Если новое верно только для части случаев (например, для одного движка озвучки), впиши его в основное правило как исключение с условием, а не вторым правилом.
- Если не ясно, кто прав (две оценки человека, два измерения), не выбирай молча. Запиши оба условия применимости или спроси человека.

Пример из практики. Музыку сначала приглушали через `sidechaincompress`, потом человек услышал «насос», и правило сменилось на ровный слой. Новое правило записали в `CLAUDE.md`, `video-voice` и `lessons.md`, а `pipeline.md` и старый урок D4 остались со старым. Через день в репозитории лежало два противоположных совета.

## 5. Формат записей

- Русский, коротко, правило в повелительной форме. Урок состоит из четырёх частей: что было, почему не заметили, правило, ловится ли скриптом.
- Пиши только то, что человек сказал или что проверено в этой работе. Догадки идут в `unverified.md`.
- Числа давай с условием и датой, если они могут устареть (цены, лимиты площадок, версии).
- Не пиши ключи API, токены, пароли, почту и личные данные человека. Имя проекта и тема допустимы.
- Имена новых файлов латиницей, `snake_case`. Навыки называй `video-…`.

## 6. Структура и нумерация

- Новые разделы в `lessons.md` добавляй в конец с заголовком `# ГГГГ-ММ-ДД. Проект. Тема`, без сквозного номера. Номера `01`–`03` в `lessons.md` и номера в заголовках файлов `reference/` историческая нумерация, не меняй и не продолжай. Два чата выберут один и тот же следующий номер.
- Не переименовывай заголовки и файлы, на них ссылаются (`lessons.md, A4`, `tts.md §6`). Ссылайся по имени файла и заголовку.
- Тело навыка держи около 100 строк. Выросло, вынеси подробности в `reference/` и оставь ссылку.
- В навыке новое правило идёт в нужный раздел, а не в «Дополнение» в конце. `name` во frontmatter не меняй. `description` меняй только если меняется момент запуска навыка.
- Добавил, переименовал или удалил файл, навык или скрипт, поправь индекс в том же коммите: таблицу «Что внутри» в `README.md` и `tools/README.md`.

## 7. Коммит

1. Один коммит, одна тема. Правило про голос и правило про площадки идут разными коммитами.
2. Запусти `python tools/check_repo.py`. Он ловит битые ссылки, навыки и скрипты без записи в индексе, маркеры слияния, повторные номера разделов и строки, похожие на ключи. Противоречия по смыслу он не видит, их ищи через `grep` (раздел 4).
3. Перед пушем снова `git pull --rebase origin main`. При конфликте слей руками, сохранив чужое. `git push --force` не используй никогда.
4. Сообщение коммита на русском: что и почему, в конце источник («ролик «Пять колец», 2026-11-16»).
5. Скажи человеку, что и куда записал и какие старые места поправил.
